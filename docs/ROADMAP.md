| 13 | **Entry flow rewrite: introduction before topic lock → inferred role → plan** | 13a ✅ (2026-08-28, v0.27.0) · 13b/13c pending | Today the most consequential choice is made when Usta knows least: pressing Enter at "What do you want to learn?" sends ONLY `mentor/PROJECT.md` to a one-shot prompt (`topic::start_suggest_system` — "propose the single best starting topic", no level criterion, no learner state), and the introduction that would learn the user runs AFTER the topic is locked (`tui/run.rs:331`, `MEET_BLOCK` at `progress.rs:48`). Honest framing for the spec: a wrong first topic costs one orphaned progress/curriculum pair and one wasted first session (a retention cost, not a disk cost) — that bug alone would justify a day of prompt work. **What justifies the rewrite is the plan feature**, which nothing in the current file set can hold. — **(A) Introduction moves before topic lock.** Not a new gated phase: the existing `MEET_BLOCK` conversation is re-ordered, so `TEACHING.md`'s "don't delay getting into the topic" is preserved — that rule guards against delaying *work*, and before topic lock the introduction IS the work of that moment. Its 1-2 question cap is deliberately dropped: depth is what makes the plan personal, and the cap was itself an untested assumption. Three rules replace the number — (i) every question must change what Usta does next (no inventory quizzing; that surfaces during work anyway), (ii) Usta reflects back what it has understood as it goes, so length reads as accumulation rather than interrogation (this is what makes a long brainstorming feel productive and a 3-question form feel long), (iii) the exit is ANNOUNCED once, plainly — "say 'let's start' any time, I'll learn the rest as we work" — and honored without argument. Boredom is NOT inferred from terse answers: the signal is confounded (a yes/no question earns a yes/no) and the codebase already bans exactly this — "your own analogies, guesses and inferences are NOT evidence" (`progress.rs:150`). Optionally one explicit fork at the natural boundary before planning ("here's what I understood — keep going or start?"). A question cap may be added LATER from real transcripts, not from fear. — **(B) Role is inferred, never asked, and is not user-scoped.** Three shapes exist — guided learning (plan is the spine) / project+teaching (plan anchored to the user's project) / observation-review (expert with an existing project wants watch mode and code critique; generating a curriculum for them is friction bordering on insult). But role is a property of the **user × domain** pair, not the user: the same person is an expert in JavaScript and a beginner in Rust on the same afternoon. So it is stored as an inferred field in the topic's approach file, following the `## Goal` precedent — "the goal is not a separate mode but an approach field... NO goal logic on the code side" (`SPEC.md:371`) — which also buys conditional prompt loading for free (`brain.rs:118-131`). Asking it as a three-way menu is the numbered-form anti-pattern `TEACHING.md:54` explicitly forbids ("infer it... ask ONE jargon-free question" only as fallback). In the observation role the plan writes itself BACKWARDS from evidence the user already produced — the Error Log's repeat counter (3+ = gap candidate) and Gaps already do this — and Usta only OFFERS a route once the ledger is thick, citing the user's own code. A plan that is earned is the only kind an expert accepts. — **(C) The plan is the curriculum file, promoted — not a seventh file.** Today's `curriculum` is a knowledge inventory (tree + `not seen`/`seen`/`settled`/`deepened`) with no ordering, no prerequisites, no "next and why". The plan is a strict superset; two model-rewritten files sharing one topic tree would reproduce inside `.usta` exactly the drift this design diagnoses in `mentor/PROGRESS.md`. Promotion also keeps the closing flush at six files (a seventh, most-structured file raises the odds of malformed output poisoning the one call that persists everything — `progress.rs:79-96`) and keeps `welcome_data`'s parsers pointed at one file. Migration is idempotent, `src/migrate.rs` precedent. What it must newly hold is the JOIN of two orderings that are NOT the same: the **build axis** (project reality — no auth before a server) and the **learn axis** (pedagogy — no ownership before variables). A milestone is chosen because it is the cheapest build vehicle for the next concept the learner needs: build step = means, concept = end. Two resolutions on purpose — the whole path stays coarse (6-10 milestones, so the learner sees where they are going) while only the ACTIVE milestone is expanded step by step, re-expanded when it completes. Three independent justifications: a 40-item visible list is an ADHD freeze trigger; a plan authored at minimum knowledge should not be the longest-lived, most detailed artifact; the file can grow without the per-session prompt growing. The FIRST milestone is explicitly a calibration milestone ("expect the plan to move after this") — the introduction yields self-report, the weakest evidence in the system, and behavioral evidence only starts once work does. — **(D) Every plan declares an end.** If a formal `## Goal` exists (certificate/exam + date + threshold, already supported) that is the end; otherwise it is a demonstrable capability the user accepts ("at the end you can build X unaided") — "learn Rust" has no completion test, "ship X unaided" does. Without a declared end there is no %, no "you are here", and re-planning has no anchor. The ROUTE is revised often and silently (at milestone boundaries); the DESTINATION is revised rarely, deliberately, and visibly — if both drift silently a moving goal always looks 80% done. — **(E) Two shell guarantees, because prompt rules are hope.** (i) Destination immutability cannot live in the closing prompt: that one LLM call already rewrites six files and has ALREADY needed shell rescue when the model dropped a single preference line (`restore_game_pref`, `lifecycle.rs:157,184`). Capture the destination before the flush, diff after, restore and SURFACE any unauthorized change. (ii) Plan→map citations need stable IDs: map items are prose lines the model may rewrite at every closing, so string references dangle within weeks and the carefully one-directional citation (plan cites map; map never knows about the plan) rots anyway. Stable IDs mean token + migration work — real cost, budget it. — **(F) One owner for "next" and one for "%".** There are THREE sources today, not two: the plan-to-be, `mentor/PROGRESS.md`'s `## Sırada` (prompt-imposed at `progress.rs:174,218`; no shell parser reads that file — it is pasted whole at `:104` — so that half is a prompt edit), and the shell itself: `next_unseen` (`tui/welcome_data.rs:73`) drives the welcome box's next-item line and `curriculum_percent` (`:54`) drives both the welcome map % and the history line. Once the plan owns "next", the welcome box will routinely contradict the opening prompt. Retiring or re-pointing `next_unseen` is a code change across `welcome_data.rs`, `welcome.rs`, and the history format. — **(G) Ownership asymmetry, stated deliberately.** The learn axis is Usta's: the user cannot hand-edit the route, because if they knew enough to edit it correctly they would not need it; they steer it through conversation ("too fast", "I don't care about X"). But `USER.md` and `mentor/PROJECT.md` ARE hand-editable by design, and the standing closing rule says "the user may have hand-edited them — don't overwrite" (`progress.rs:146`) — so build-axis assertions ("the Friday demo needs auth") are accepted as facts, not negotiated. — **(H) Blockers and unsettled items the spec must close.** (1) The observation role has NO topic, yet every path is topic-keyed — `build_session` (`lifecycle.rs:48`), the progress/curriculum/approach paths (`progress.rs:14-31`), the lock (`:289`), the catalog, the transcript name; a per-project pseudo-topic needs its slug, lock and index semantics designed, and this blocks the file model. (2) The introduction's diagnostic output has no home: the profile explicitly bans topic knowledge (`progress.rs:150`) and the progress file needs the topic the introduction deliberately does not yet have. (3) First-run detection cannot ride on `profile_is_generic` — it is an exact-match against the embedded template (`setup.rs:319`) whose own text invites hand-editing, so one edit skips the introduction forever and a reset re-triggers it for a veteran; it needs its own persisted marker. (4) The whole design is written in TUI terms; `src/plain.rs` has its own `resolve_topic`/onboarding path (`:41,188,222`) — does pipe/CI skip the introduction permanently or block on it (which breaks CI)? (5) Abandoning a plan leaves a dead artifact frozen at N% — the exact guilt object this codebase makes structurally unprintable elsewhere (`streak: 0` can never be printed, SPEC v0.15/v0.17); pausing/abandoning needs the same ADHD-safe treatment (archive and reframe, never "40% and stopped"). (6) On mis-self-assessment (an expert picks observation, basic gaps surface) Usta logs and makes the evidence-based route offer and never forces a role change — but not silently: a user-readable ledger revealed later as "you've hit this three weeks running" reads as surveillance, so say once that recurring patterns are being noted. — **Staging**, each independently useful: **13a** introduction before topic lock + the three conversation rules + inferred role field + the suggestion finally seeing the learner (kills `start_suggest_system` and its yes/no confirm gate; needs blockers H2 + H3 closed). **13b** curriculum promotion + stable map IDs + destination restore + plan generation + entry-point derivation + single owner of next/% (needs H1 closed). **13c** re-planning at milestone boundaries, the earned-plan offer, role transitions in both directions, and ADHD-safe plan abandonment (H5). Each stage gets its own spec → plan → implementation cycle. |

## Tech debt / small items

- `run_plain_loop` has 10 args (pre-existing clippy `too_many_arguments`) — needs a real signature refactor (params struct); deliberately left, open as its own small task.
- Conditional loading for `approaches/_default.md` (only needed during new-topic onboarding) and `learner/index.md` (catalog rarely needed inside a single-topic session) — low-priority follow-up to #9.
- **Clear the screen on launch** (unscheduled, decided 2026-08-28): today Usta starts inside whatever the shell already printed — old command output stays above the inline viewport and the session opens on a dirty slate. Wanted: wipe the terminal at startup so the session begins on a clean screen. Mechanics: `Clear(ClearType::All)` + `MoveTo(0, 0)` inside `term::setup()`, and it MUST run *before* the one real `cursor::position()` CPR seed (`src/tui/term.rs:54`) — seeding first and clearing after would leave `TrackedBackend` holding a stale row and re-open the crash class the CPR fix closed. Open questions: whether scrollback is erased (`ClearType::Purge`) or only the visible screen; whether it applies to the plain/pipe path (it should not) and to `usta start <topic>`; whether it needs an opt-out for users who want their prior output kept.
- Further ideas (unscheduled): streaming replies, multi-terminal hardening, self-health-check (links/consistency), tech-notes cache.

## Completed

- 2026-08-28: Watcher turn-taking — the watcher never initiates an LLM turn (no exceptions, `exercises/` included): a flushed debounce batch is held in `PendingChanges` (paths only, order kept, dedup'd) and rides along with the user's NEXT message as one combined call — file block first, user's words last; the payload is built at delivery time (`deliver_pending`) so intermediate saves collapse into one diff and meanwhile-deleted files drop out. Presence is deterministic: the status line counts `👁 watching · N changes noted`, reset on delivery, zero tokens (no LLM-generated ambient text, ever). Immediate feedback survives as an explicit user choice — `/watch live [on|off]` replaces `/watch polite`, and the approach file's `watch: live` line now selects timing (immediate + plain review frame) instead of frame: `watching`+`polite` collapse into one honest axis (companion = accumulate + `flow_frame` · live = immediate + `feedback_frame`). Prompt side (backup layer, not the primary defense): eyes-only rule (assignment artifacts are verified against the user's report, never narrated), one-sentence nudge instead of full question repeats, TEACHING.md no longer promises "saving triggers your review". `Cargo.lock` joins the watcher's ignore list. Pending changes are dropped silently on `/quit`/close (the closing flush already reads disk); a bulk batch never enters the pending set. Design: `docs/superpowers/specs/2026-08-28-watcher-turn-taking-design.md`. v0.28.0.

- 2026-08-27: CPR race fix — upstream ratatui issue #2640 is open and unresolved: inline-viewport operations (`insert_before`, which ends in a `Terminal::clear()`, `compute_inline_size` at init/resize) each write a cursor-position (CPR) query to stdout whose reply arrives on stdin, and when a `crossterm::EventStream` already holds the stdin reader lock the reply is never delivered and the query times out fatally (`Error: The cursor position could not be read within a normal duration`). Fixed on our side without waiting on upstream: `src/tui/backend_wrap.rs`'s `TrackedBackend<W>` wraps `CrosstermBackend` and answers `get_cursor_position()` from cursor state it tracks itself, so no CPR query reaches stdin during the session; the one real CPR query now happens exactly once, in `term::setup()`, before any `EventStream` is constructed, purely to seed that tracked state. Eliminates the fatal crash class entirely; the upstream bug itself remains open. Design: `docs/superpowers/specs/2026-08-27-cpr-race-fix-design.md`. v0.26.1.

- 2026-08-27: ratatui 0.30 migration — bumped ratatui 0.29.0 → 0.30.2 (crossterm unified on 0.29.0 across the tree, `cargo tree -i crossterm` proves a single version) to pick up the upstream fix for inline-viewport horizontal-resize garbling (ratatui issue #2086, resolved by PR #2355). `page::handle_resize` simplified to `autoresize()` alone — the manual `clear()` from the v0.24.6 workaround is no longer needed since 0.30's resize path clears the viewport itself.
